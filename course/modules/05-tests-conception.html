[Fact]
public void OrderKeepsOriginalPrice()
{
    var product = new Product("Clavier", 30m);
    var order = new Order();
    order.AddItem(product, 2);

    product.Update("Clavier", 50m);

    Assert.Equal(60m, order.Total);
}
Arrange → Act → Assert

Le test instancie directement le domaine. Aucun serveur, conteneur DI ou fichier SQLite n'est nécessaire pour vérifier cette règle.

Un bon test doit devenir rouge si le comportement protégé est cassé.

Le fake ne simule pas EF Core dans son ensemble. Il reproduit seulement le comportement nécessaire pour montrer qu'un produit reste « en attente » tant que SaveChangesAsync n'a pas été appelé.

Intégration ≠ « test lent ». La distinction porte surtout sur le nombre de composants réellement traversés.

Strategy : nommer un besoin déjà compris

public interface IShippingStrategy
{
    decimal Calculate(decimal subtotal);
}

public class Checkout
{
    private readonly IShippingStrategy _shipping;
    public Checkout(IShippingStrategy shipping) => _shipping = shipping;
    public decimal Total(decimal subtotal)
        => subtotal + _shipping.Calculate(subtotal);
}
Pourquoi introduire le pattern ?

Le calcul de livraison varie. Plutôt qu'empiler les conditions dans Checkout, on injecte l'algorithme.

Le pattern ne remplace pas les bases : interface, composition et polymorphisme étaient déjà connus.

Défi autonome : renommer sans toucher au prix

PATCH /products/{id}/name

Le JSON ne contient que le nouveau nom. Le domaine réutilise sa règle existante, la persistance est sauvegardée, aucune migration n'est nécessaire et les anciennes lignes de commande gardent leur nom/prix historiques.
